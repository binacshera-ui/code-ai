# ארכיטקטורת מעבר: סוכן הקוד ממסלול JSON למסלול Tools

## מטרת המהלך

המטרה היא להעביר את סוכן הקוד ממודל שבו הוא מחויב להחזיר בכל סבב `JSON` טקסטואלי בסגנון:

- `thought`
- `plan`
- `tool`
- `action`
- `params`
- `config`

למודל מקצועי יותר שבו המודל קורא לכלים אמיתיים, והשירות הוא זה שמבצע:

- ולידציה קשיחה
- ניתוב
- רישום מצב
- הרכבת דוח לקוח

בלי להכריח את המודל לנסח חוזה פעולה בתוך טקסט.

## מסקנה מרכזית

המעבר נכון ורצוי, אבל לא נכון לבצע אותו כמעבר "בבת אחת" ל־tools native בלי שכבת בקרה קשיחה.

הסיבה:

1. שירות `gemini-conversation-service` כבר תומך ב־tools ברמת Gemini.
2. בפועל, בניסוי חי, המודל אכן החזיר `functionCall`.
3. אבל באותו ניסוי התגלו גם בעיות שמחייבות שכבת guard:
   - חזרה של prose יחד עם tool call
   - בחירת כלי שלא קיים ב־allowlist
   - התנהגות לא אחידה בין מסלול Vertex למסלול API key

לכן הארכיטקטורה הנכונה היא:

- `native tool calling` ברמת המודל
- `hard server contract` ברמת השירות
- `dynamic tool registry` כדי לא להציף את המודל

## ממצאי הניסוי הקטן

ניסוי חי בוצע מול `gemini-conversation-service` עם `gemini-3.5-flash` ו־tool schema פשוט.

### ממצא 1: native tools עובדים

בקריאה ישירה ל־`/chat` המודל החזיר `functionCall` ב־payload של Gemini.

כלומר:

- המעבר לכלים הוא לא רעיון תיאורטי
- יש תשתית חיה שאפשר להישען עליה

### ממצא 2: strict לא מספיק לבד

בניסוי עם `strict_tools_mode=true`, המודל עדיין החזיר טקסט, ובמקרה אחר אפילו `JSON` טקסטואלי במקום function call נקי.

כלומר:

- אי אפשר לסמוך על strict mode לבדו
- חייבים validator שמזהה ומתקן סטיות

### ממצא 3: model יכול לבחור tool שגוי

בניסוי אחד המודל קרא ל־`default:directory_list`, ובניסוי אחר הוא כתב `execute_bash`, למרות שכלים כאלה לא הוגדרו ב־request.

כלומר:

- חייב להיות `tool allowlist`
- כל tool שלא רשום חייב להידחות אוטומטית
- הדחייה צריכה להפעיל correction turn, לא לקרוס

### ממצא 4: מסלול Vertex אצלכם עדיין לא נורמל לגמרי לכלים

בלוגים חזר:

- `tools[0].tool_type: required one_of 'tool_type' must have one initialized field`

כלומר:

- ה־payload בפורמט OpenAI-like לא מתורגם עדיין בצורה מלאה לפורמט Gemini/Vertex tool declarations
- לפני מעבר מלא, חייבים ליישר את שכבת התרגום הזאת

## מה לא טוב במבנה הנוכחי

המסלול הנוכחי מכריח את המודל לבצע יותר מדי עבודת serialization במקום עבודת agent:

1. הוא לא רק מחליט מה לעשות, אלא גם כותב את החוזה בפורמט JSON.
2. הוא נושא כל turn גם `thought` וגם `plan` וגם `tool/action/params/config`.
3. השירות נאלץ:
   - לפרסר טקסט
   - לתקן JSON
   - להעביר דרך TextMaster
   - לנרמל שוב
   - לתקן contract errors
4. חלק מן הכפילויות בדוחות נולדות כי יש גם "החלטת סוכן" טקסטואלית וגם "תוצאת כלי" וגם "פלט callback".

במילים פשוטות:

- היום המודל כותב גם את ההחלטה וגם את מעטפת ההפעלה
- המערכת אחר כך מנסה לנחש מה היה "באמת"

המהפך הנכון הוא:

- המודל מחליט
- הכלי נקרא
- השרת שומר מצב

## עקרון התכנון החדש

### עיקרון 1: model calls tools, not JSON envelopes

במקום:

- `tool=dev_ops`
- `action=batch_smart_apply`
- `params.operations=[...]`

המודל יקרא ישירות לכלי:

- `batch_smart_apply(...)`

או:

- `read_file(...)`
- `search_code(...)`
- `lint_project(...)`
- `finish_task(...)`

### עיקרון 2: לא מציפים את המודל בכלים

לא נכון לחשוף בכל turn את כל ארסנל היכולות.

הפתרון:

- mount דינמי של כלים לפי שלב
- mount דינמי לפי tier
- mount דינמי לפי מצב פרויקט

### עיקרון 3: plan הוא state, לא פורמט תגובה

`plan` לא צריך להופיע בכל response של המודל.

אם רוצים לשמר state של תכנון, צריך להחזיק אותו כ־artifact פנימי:

- או tool פנימי `sync_plan`
- או state server-side שמתעדכן רק כשיש שינוי מהותי

אבל לא לכפות על המודל לכתוב `plan` בכל turn.

### עיקרון 4: customer report צריך להיבנות מכלים שבוצעו, לא ממחשבות

הדוח ללקוח צריך להיגזר מ:

- אילו כלים הופעלו
- אילו קבצים השתנו
- אילו בדיקות עברו או נכשלו
- מה סוכן הקוד מסר בסיום

ולא מ:

- `thought`
- `plan`
- טקסטי החלטה ביניים

## שכבת guard שחייבת להיבנות

### 1. Unknown tool rejection

אם המודל קרא לכלי שלא קיים:

- לא לבצע כלום
- לא לקרוס
- לרשום event
- להחזיר correction turn:
  - "בחר כלי מתוך הרשימה המותרת בלבד"

### 2. Args validation

כל tool חייב schema קשיח.

אם args לא תקינים:

- correction turn
- לא לבצע

### 3. Provider normalization

השרת חייב לנרמל tool schemas בנפרד ל:

- Gemini API key mode
- Vertex mode

בלי להניח שפורמט OpenAI-like יעבוד אוטומטית.

### 4. Text leakage protection

אם המודל החזיר prose יחד עם tool call:

- ignore את ה־prose ברמת orchestration
- keep רק function call
- לא לשלב את ה־text הזה בדוח לקוח

### 5. Tool replay safety

צריך idempotency key לכל tool execution:

- כדי לא להפעיל אותו פעמיים אם model/transport חוזר על אותה קריאה

- `code_plan` יהפוך ל־`tool_call_decision` או `plan_sync`, לא JSON blob

## ההחלטה הארכיטקטונית שאני ממליץ לאשר

1. סוכן הקוד עובר מ־JSON envelope ל־native tool calling.
2. שומרים את היכולות הקיימות, לא שוברים service-a.
3. מצמצמים את הפרומפט ל־policy בלבד.
4. מעבירים schema ותחביר לכלים עצמם.
5. מוסיפים `sync_plan` פנימי.
6. מעלים rollout בשכבות, לא ב־big bang.
