# Code‑AI Workbench

`app-code-ai.bina-cshera.co.il` הוא משטח עבודה ייעודי לבדיקת אתרים ולתיקונם בעזרת Code‑AI. הוא אינו מחליף את `app-codex.bina-cshera.co.il` ואינו משנה את ממשק Code‑AI הרגיל.

## חוויית המשתמש

1. נכנסים ל־`app-code-ai.bina-cshera.co.il` ופותחים את המכשיר מתוך פאנל Code‑AI.
2. סביבת Chromium מבודדת נפתחת אוטומטית עבור שיחת Codex הפעילה.
3. לאחר פתיחת המכשיר, ה־Workbench מבקש מהשרת סשן עבודה ייעודי וקצר־מסלול עבור `app.bina-cshera.co.il`, ומחבר אותו לדפדפן המבודד — בלי מסך כניסה נוסף ובלי להעביר סיסמה לדפדפן.
4. מזינים בסרגל העליון כתובת אתר. האתר נטען בתוך הדפדפן המרוחק, ולכן הוא אינו תלוי בהרשאות `iframe` של האתר הנבדק.
5. אפשר לגלוש, להקליד, לגלול, לחזור, לרענן, לפתוח טאבים ולבדוק תצוגת מחשב, טאבלט או טלפון.
6. במצב בחירה לוחצים על אלמנט אחד; במצב בחירה מרובה מצרפים כמה רכיבים; ובמצב אזור גוררים מלבן חזותי.
7. הבחירה מופיעה גם מעל התצוגה וגם ליד תיבת הכתיבה של Code‑AI. שליחת ההודעה מוסיפה למנוע הקשר מובנה, אך בתמליל המשתמש נשאר רק הטקסט שהקליד.

פאנל השיחה הקיים של Code‑AI מוצג בצד ימין של משטח העבודה. זהו אותו `/chat` ללא עיצוב מחדש של ממשק ה־AI; רק מיקום חלונית ה־Workbench השתנה.

תצוגת האתר מגיעה כזרם MJPEG חי מ־Chromium דרך CDP, באיכות JPEG גבוהה וללא buffering ב־Nginx. צילום המסך האחרון נשמר מתחת לזרם כ־fallback, כך שבחיבור מחדש או בדפדפן שאינו תומך ב־CDP אין הבהוב ואין מסך ריק. סנכרון הרקע החי מעדכן רק metadata; צילום מחזורי נשאר פעיל רק במצב fallback.

קלט רציף אינו עובר במסלול פעולות הצילום: תנועות עכבר במצב גלישה נדגמות ומאוחדות אל המיקום האחרון, וגלילות סמוכות מצטברות ונשלחות אל Chromium כאירועי `mouse.wheel` אמיתיים. `/api/codex/session-browser-viewer/input` מחזיר `202` מיד, וה־runtime מעבד את הקלט לפי סדר הפעולות בלי להציג שכבת טעינה ובלי ליצור JPEG חדש אחרי כל אירוע. לחיצות, הקלדה וגרירה משתמשות גם הן בזרם החי ואינן מציגות את שכבת "מעדכן תצוגה" כאשר הזרם תקין.

השינוי הזה תחום לדפדפן הפנימי: `/chat`, ה־composer, תמליל השיחה וכל ממשק ה־AI ממשיכים להיטען דרך ה־iframe הקיים ולא שונו.

ה־viewer וכלי הדפדפן של ה־AI אינם מפעילים עוד שני Chromium נפרדים. ה־viewer מחזיק runtime יחיד לכל סשן, ו־MCP של Codex פועל כפרוקסי stdio קל אל גשר loopback מאומת של אותו runtime. לכן `tabId`, הטאב הפעיל, URL, cookies ומצב העמוד זהים בצד המוצג ובצד שמופעל בידי המנוע. lease שנלקח לכל משך ריצת Codex מונע מסגירת ה־runtime באמצע ריצה גם כאשר ממשיכים את השיחה מתוך `app-codex` ללא תצוגת הדפדפן.

## נתיבי סשן ועבודה מקבילית

כל טאב חיצוני מקבל נתיב קנוני שמכיל את זהות הפרופיל והסשן שלו:

```text
/session/<profileId>/<sessionId>
/session/<profileId>/draft/<draftKey>
```

פתיחת כתובת הבסיס בטאבים נפרדים יוצרת `draftKey` שונה בכל טאב ומחליפה את ה־URL באמצעות `history.replaceState`, ללא reload. אחרי ההודעה הראשונה אותו נתיב מוחלף אטומית ל־UUID האמיתי של השיחה. בחירת שיחה קיימת משנה רק את הנתיב וה־state של הטאב שבו בוצעה הבחירה.

ה־iframe הימני מקבל נתיב מקביל תחת `/chat/session/...`, ולכן הוא אינו יכול לעלות זמנית על סשן אחר בזמן bootstrap. ה־Workbench מתעלם מהודעות context זמניות שאינן תואמות למזהה שבנתיב עד שהטעינה של הסשן המבוקש הסתיימה.

הפרדת ה־runtime ממשיכה להיעשות באמצעות הצמד `profileId + sessionKey`. גם כתובת האתר הפנימית נשמרת במפתח storage שכולל את אותו צמד; אין עוד כתובת יעד גלובלית שיכולה לעבור מטאב אחד לאחר. שתי כתובות סשן שונות מקבלות תיקיות פרופיל Chromium שונות, בעוד פתיחת אותו נתיב פעמיים משתפת בכוונה את אותו דפדפן ואותם טאבים.

אותו נתיב פועל גם ב־`app-codex`: שם מוצג רק ממשק השיחה, אך הוא ממשיך להיות קשור לאותו runtime. קישורי query ישנים מסוג `?profile=...&session=...` עדיין נקראים ומומרים לנתיב הקנוני לצורך תאימות לאחור.

## חיבור מאובטח לאתרי Bina

- רק משתמש Code‑AI מאומת שמכשירו פתוח רשאי לבקש חיבור. שרת Code‑AI אינו משתמש בסיסמת אתר ואינו שולח secret לדפדפן; הוא חותם על בקשה פנימית קצרת־תוקף אל Bina 3.0.
- שירות Bina 3.0 מאמת HMAC על הגוף המדויק, חלון זמן של 60 שניות, `audience` קבוע ו־nonce חד־פעמי המונע replay. נקודת הקצה הפנימית מקבלת תעבורה מ־loopback בלבד.
- לאחר האימות, Bina 3.0 יוצר session עצמאי במסד הסשנים הרגיל. רק מזהה הסשן האטום עובר ישירות לערוץ הבקרה הפרטי של Chromium ומותקן כ־`bina_rt_sid` עם `Secure`, `HttpOnly`, `SameSite=Lax`, ורק עבור `app.bina-cshera.co.il`.
- תמיכה אופציונלית בשירותים הוותיקים מאמתת בנפרד `forum.session` מול שירות auth פנימי; cookie ותיק אינו תנאי לכניסה אל Bina 3.0 ואינו מוחלף ב־cookie החדש.
- ערוץ הבקרה מקשיב רק ל־loopback, דורש token אקראי לכל runtime, וקובץ הגילוי שלו נשמר בהרשאת `0600`. פעולת החיבור אינה כלי MCP ואינה זמינה למודל.
- מזהי session ו־secrets אינם מוחזרים ללקוח, אינם מוכנסים ל־prompt ואינם נכתבים ללוג. כשל בחיבור מנקה cookies ישנים מהפרופיל המרוחק ואינו עוצר גלישה באתרים אחרים.
- `BINA_RUNTIME_INTERNAL_ORIGIN` מוגבל ל־loopback ו־`BINA_WORKBENCH_SSO_SECRET_FILE` מצביע לקובץ secret בהרשאת `0600`; כתובת היעד וה־cookie names קבועים בקוד ואינם מגיעים מקלט המשתמש, כדי למנוע SSRF או הזרקה לדומיין אחר.

## ההקשר שנשלח למנוע

לכל אלמנט מצורפים, לפי הזמינות:

- כתובת העמוד, כותרת הטאב וגודל ה־viewport.
- צילום מסך מלא וחיתוך של האלמנט.
- `tag`, תפקיד נגיש, שם נגיש וטקסט מקוצר.
- selector ראשי ומועמדי selector מדורגים.
- מלבן האלמנט, שרשרת אבות, נתיב `iframe` ונתיב Shadow DOM.
- תת־קבוצה שימושית של computed styles וכללי CSS תואמים שנגישים לדפדפן.
- רמז לקובץ ולרכיב, כאשר האתר מספק Source Bridge.

שדות סיסמה, פרטי כרטיס, token או secret מסומנים כרגישים. הערך שלהם לעולם אינו מוחזר לממשק או להודעת המנוע.

## Source Bridge אופציונלי

באתר שנמצא בפיתוח אפשר להוסיף לאלמנטים מידע מדויק על מקורם:

```html
<button
  data-code-ai-source="src/components/CheckoutButton.tsx:42:7"
  data-component="CheckoutButton"
>
  לתשלום
</button>
```

אפשר להשתמש גם ב־`data-source`. בלי bridge, המערכת עדיין מעבירה selectors, סגנונות ומבנה DOM, ו־Code‑AI מאתר את המקור בריפו.

## גבולות השירות

- `/` ו־`/workbench` בדומיין `app-code-ai` פותחים את ה־Workbench.
- `/session/<profileId>/<sessionId>` פותח Workbench שמקובע לסשן מסוים; נתיב `draft` מקבע טאב חדש עוד לפני יצירת UUID אמיתי.
- `/chat` מציג בתוך הסיידבר את ממשק Code‑AI הקיים.
- `/api/codex/session-browser-viewer/stream` מעביר ללקוח זרם MJPEG מאומת מתוך ה־runtime המקומי; נקודת ה־CDP עצמה נשארת ב־loopback ודורשת token פרטי.
- `/api/codex/session-browser-viewer/input` מקבל ריחוף וגלילה בתדירות גבוהה, מאחד אירועים עודפים ומחזיר `202` בלי להמתין לצילום מסך.
- `app-codex` ממשיך להציג את הממשק הרגיל בלבד.
- הדפדפן נשמר לפי סשן וממוחזר במעבר אטומי ממזהה שיחה זמני ל־UUID האמיתי. המעבר אינו מייצר draft ביניים חדש, אינו מנווט מחדש את העמוד ואינו מאפס את ה־viewer לאחר ההודעה הראשונה.
- פתיחת אותו UUID מתוך `app-codex` משתמשת באותו runtime ובאותו פרופיל. אין שם חצי תצוגה חזותי, אך כלי MCP ממשיכים לעבוד על אותם טאבים.
- runtime שלא היה פעיל במשך 15 דקות נסגר אוטומטית. לפני הסגירה נשמרים רשימת הטאבים והטאב הפעיל בקובץ session פרטי בהרשאת `0600`; בהמשך הם משוחזרים יחד עם פרופיל ה־Chromium.

## פריסה

שער השירותים צריך לכלול את שני הכינויים, בלי להפנות ביניהם:

```text
codex  -> http://localhost:4000
code-ai -> http://localhost:4000
```

ההבחנה נעשית בצד הלקוח לפי hostname. התצורה הזאת מאפשרת לשני המוצרים לחלוק את מנגנון ה־auth, ה־queue ומנוע Codex, תוך שמירה על שתי חוויות כניסה ועוגיות פתיחת־מכשיר נפרדות.

בדיקות בריאות מומלצות לאחר פריסה:

```bash
curl -fsSI https://app-codex.bina-cshera.co.il/
curl -fsSI https://app-code-ai.bina-cshera.co.il/
curl -fsS https://app-code-ai.bina-cshera.co.il/api/codex/auth/status
```

בדיקת E2E מלאה כוללת התחברות, פתיחת URL, מיקום פאנל ה־AI מימין, זרם Chromium חי, ריחוף וגלילה דרך נתיב הקלט המהיר, היעדר שכבת טעינה בזמן wheel, מעבר viewport והתאמה לרוחבי מסך שונים. `test:workbench:parallel-tabs:e2e` פותחת שני נתיבי סשן בשני טאבים חיצוניים, מנווטת כל runtime לכתובת אחרת, ומוודאת שהנתיב, תיקיית הפרופיל והכתובת נשמרים בנפרד גם אחרי reload. בדיקת ה־runtime מאמתת בנוסף ש־MCP וה־viewer רואים אותו `tabId`, ששינוי DOM דרך MCP נראה מיד ב־viewer, ושני טאבים והטאב הפעיל נשמרים לאחר rebind ולאחר restart.
