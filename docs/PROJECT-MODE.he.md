# מצב פרויקט UI/Product

מצב פרויקט הוא orchestrator כללי לבניית ושיפור מוצרי UI המחוברים לבקאנד
אמיתי. הוא אינו קשור למותג, לעולם, לפורט או למערכת עיצוב מסוימים. ה־UI
שכבר רץ בפורט נחשב יעד חי שיש להבין ולפתח, אלא אם המשתמש בחר במפורש
מדיניות החלפה.

## תנאי הפעלה

השרת דוחה הפעלה כאשר אחד מן התנאים הבאים אינו מתקיים:

- פרופיל העבודה הוא Codex;
- נבחר פרופיל Gemini מורשה;
- פורט UI חוקי פתוח על `127.0.0.1` — גם דף ריק מספיק;
- תיקיות frontend ו־backend קיימות, נגישות ובתוך שורשי השרת המותרים;
- הוגדרו שם, בריף, תוצאה ראשית, קהל, ארכיטיפי משתמש, אסכולת UX,
  תחושה חזותית וגופן;
- ששת צבעי התפקיד הם ערכי hex תקינים.

הפורט והתיקיות נבדקים שוב לפני יצירת תוכנית עבודה, כדי למנוע תור ארוך
שמתחיל מול יעד שנעלם.

## חוזה הקלט

`CodexSessionProjectMode` מחזיק:

- זהות הפרויקט וחשבון Gemini;
- URL מקומי הנגזר מפרוטוקול ומפורט;
- תיקיות frontend, backend ומערכת עיצוב אופציונלית;
- בריף, הקשר עסקי, תוצאה, קהל, ארכיטיפים ומחקר משתמש;
- שפת תוכן, locales, נגישות, responsive ודרישות analytics;
- אסכולת UX, תחושת מותג, גופן ופלטת תפקידים;
- פלטפורמה, כיווניות וחוזה פשוט/מקצועי;
- רפרנסים, אילוצים וקריטריוני הצלחה;
- מדיניות שימור ה־UI הקיים;
- היקף תוכנית ומספר סוכנים מקביליים;
- תוצאת בדיקת הפורט ותיקיית ארטיפקטים פרטית.

אין לשמור סיסמאות, cookies או tokens בתוך שדות הבריף והרפרנסים.

## מודל העבודה

ה־runtime משלב ארבעה דפוסים:

1. workflow דטרמיניסטי הקובע סדר ושלבי קבלה;
2. supervisor של Codex האחראי להחלטה ולמיזוג;
3. סוכני Codex מקבילים בעלי תפקידים ותחומי כתיבה צרים;
4. generator/critic שבו Gemini מספק ביקורת UX ועיצוב ו־Codex מבצע ומאמת.

שמירת מצב פעיל מפעילה אוטומטית:

- Native Multi-Agent של Codex;
- Design Mode בעומק `deep`;
- UX Mode בעומק `deep` ובמודל `gemini-3.1-pro-preview`;
- Browser Mode מבודד ו־headless בעת הריצה, אם לא נבחר דפדפן אחר.

מצב סוכנים נפרד, מצב מקצועי, מצב מטרה, מצב ביאורים והגבלת פעולה
חד־נתיבית אינם ניתנים לשילוב באותה שליחה. מצב פרויקט כבר מחזיק את
הפונקציות האלה במסגרת תוכנית אחת.

## תוכנית Enterprise

תוכנית Enterprise מייצרת שמונה משימות רצופות באותו queue ובאותו סשן:

1. baseline, מפת מקור אמת ו־Project Charter;
2. מודל מוצר, משתמשים, הרשאות ומסעות;
3. שפה חזותית ו־Design System;
4. Screen Specs, registry, רכיבים וניסוחים;
5. יישום יסודות ומעטפת;
6. יישום מסכים, מסעות וחיבורי backend;
7. ביקורת UX, Design, נגישות, responsive ופוליש;
8. בדיקה מקצה לקצה ומסירת ראיות.

תוכנית `full` משתמשת בשישה שלבים ותוכנית `focused` בארבעה. כל משימה
מקבלת מחדש את חוזה הפרויקט המלא, ולכן התור ניתן לחידוש גם אחרי restart.

## כללי איכות

- אין לייצר מסך לכל endpoint; מסכים נגזרים מתוצאות, ישויות, תפקידים,
  lifecycle, מסעות והרשאות.
- אין להעתיק ממשק של חברה אחרת. רפרנסים מגדירים איכות, תחושה ועקרונות.
- כל מסך כולל loading, empty, error, permission, offline ו־recovery.
- החלטת UX משמעותית מתחילה בעמדת Codex פרטית ובשאלה ניטרלית ל־Gemini.
- Gemini Design רשאי להציע ולהעביר ביקורת; Codex נשאר בעל הקוד והאימות.
- בדיקות browser, responsive, RTL/LTR, keyboard, focus, accessibility
  ו־console הן חלק משער הקבלה.
- מחיקה, פריסה או פעולה חיצונית משמעותית נשארות כפופות להרשאות ולמדיניות
  הסשן; עצם הפעלת מצב פרויקט אינה אישור לפעולה בלתי הפיכה.

## API

- `GET /api/codex/session-project-mode`
- `POST /api/codex/session-project-mode`

ה־POST מחזיר גם את מצבי Design ו־UX שנוהלו עבור הפרויקט. שגיאת port או
path מוחזרת כ־JSON עם HTTP 400; לעולם אין fallback ל־HTML או להפעלה חלקית.
